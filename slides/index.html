Introdução

Onde entra o teste de segurança

  • Teste funcional: o sistema faz o que foi pedido?
  • Teste não funcional: como ele se comporta — desempenho, confiabilidade, usabilidade e segurança.
  • Security Testing: verifica se o sistema continua protegendo dados e funções quando alguém tenta, de propósito, fazê-lo falhar.
  • O "usuário" do teste é um adversário inteligente, não um usuário comum.
  • Testa principalmente requisitos negativos: o que o sistema não deve permitir (POTTER; McGRAW, 2004).
Exemplo: "ninguém deve entrar sem a senha certa" e "um recado não pode executar código no navegador de quem lê".
Introdução

Por que testar segurança?

  • Software funcionalmente correto pode ser inseguro. No nosso exemplo, a tela de login e o mural funcionam — e mesmo assim são exploráveis.
  • Falhas de segurança quase nunca aparecem no uso normal: aparecem com entradas maliciosas.
  • Quanto mais tarde a falha é descoberta, mais cara é a correção (McGRAW, 2006).
  • Consequências de uma falha explorada: vazamento de dados, fraude, indisponibilidade, prejuízo financeiro e de imagem.
  • Segurança não se adiciona no final: precisa ser verificada durante todo o desenvolvimento.

O que é e qual o propósito

O que é Security Testing?

  • Myers, Sandler & Badgett (2011): elaborar casos de teste que tentam subverter as verificações de segurança do programa.
  • Pressman & Maxim (2016): verificar se os mecanismos de proteção de fato protegem contra acesso indevido.
  • Felderer et al. (2016): validar os requisitos de segurança e identificar vulnerabilidades.

Duas frentes complementares (POTTER; McGRAW, 2004)

🔐 Testar os mecanismos
login, permissões, criptografia — parece teste funcional
🕵️ Teste baseado em risco
pensar como o atacante e procurar o que ninguém especificou

Pode ser aplicado em todos os níveis: unidade, integração e sistema.

O que é e qual o propósito

Qual o propósito?

  • Encontrar vulnerabilidades antes que um atacante encontre.
  • Verificar se os controles funcionam: autenticação, autorização, validação de entrada.
  • Medir e reduzir o risco: priorizar o que causa maior impacto.
  • Evitar regressão: um teste de segurança automatizado roda a cada alteração do código.
  • Produzir evidência objetiva de que os requisitos foram verificados.
Limite importante: o teste mostra a presença de vulnerabilidades, nunca a ausência delas (MYERS; SANDLER; BADGETT, 2011).

Prós, contras e ferramentas

Vantagens e desvantagens

Vantagens

  • Encontra falhas que o teste funcional não vê
  • Corrigir cedo custa menos que corrigir após incidente
  • Pode ser automatizado e repetido a cada alteração
  • Existem ferramentas maduras e gratuitas
  • Gera evidência objetiva dos requisitos

Desvantagens

  • Não prova que o sistema está seguro
  • Falsos positivos (SAST) e falsos negativos (DAST)
  • Exige conhecimento especializado
  • Ferramentas não entendem regra de negócio
  • Precisa de manutenção: surgem falhas novas o tempo todo

Exemplo prático

Estratégia do repositório: duas branches

branch vulneravel

  • SQL concatenado no login
  • Recado renderizado com |safe
  • Os dois ataques funcionam

branch corrigido

  • Consulta parametrizada (?)
  • Escape automático do Jinja2
  • Os dois ataques são bloqueados
A diferença entre as versões é exatamente o conserto. Basta trocar de branch para ver a falha aparecer e sumir: 
git diff vulneravel corrigido -- app/
Demo 1 · SQL Injection · A03

Código vulnerável e o ataque

Login (branch vulneravel)

# a entrada do usuário é concatenada direto na string SQL
sql = "SELECT * FROM users WHERE username = '%s' AND password = '%s'" % (u, p)
user = db.execute(sql).fetchone()

Ataque no formulário de login

usuário:  admin' --
senha:    (qualquer coisa)
O -- transforma o resto da consulta (a checagem de senha) em comentário. Resultado: login como admin sem a senha.
Demo 1 · SQL Injection · correção

Correção: consulta parametrizada

Login (branch corrigido)

# os valores vão como parâmetros — nunca viram comando SQL
user = db.execute(
    "SELECT * FROM users WHERE username = ? AND password = ?",
    (username, password),
).fetchone()
  • O driver trata admin' -- como um texto de login, que simplesmente não existe.
  • Mesma regra vale para qualquer payload: ' OR '1'='1, ' UNION SELECT…
O ataque passa a devolver "usuário ou senha inválidos". ✓

Em produção: somar hash de senha (bcrypt) em vez de comparar texto puro.

Demo 2 · Stored XSS · A03

Código vulnerável e o ataque

Template do mural (branch vulneravel)

<p>{{ c.content | safe }}</p>   <!-- desliga o escape do Jinja2 -->

Ataque: publicar este recado

<script>alert('XSS de ' + document.domain)</script>
O recado fica salvo no banco. Todo mundo que abrir o mural executa o script do atacante — por isso stored (persistente).
Demo 2 · Stored XSS · correção

Correção: deixar o Jinja2 escapar

Template do mural (branch corrigido)

<p>{{ c.content }}</p>   <!-- escape automático ligado -->
  • O Jinja2 converte < > & " em entidades HTML.
  • O <script> aparece como texto na tela e não executa.
  • Princípio: output encoding — tratar dado do usuário como dado, nunca como código.
O recado malicioso vira texto inofensivo. ✓

Reforços: Content-Security-Policy e sanitização de HTML quando se quer permitir formatação.

Conclusão

O que levar desta apresentação

  • Teste funcional não basta: a versão vulnerável funcionava.
  • Security Testing verifica o que o sistema não deve permitir, pensando como o atacante.
  • As duas falhas vêm da mesma raiz: misturar dado com código (SQL e HTML).
  • A correção é separar dado de código: parametrizar consultas e escapar a saída.
  • Nenhuma técnica sozinha resolve — SAST, DAST e testes se complementam.
  • O teste reduz o risco, mas não prova que o sistema é seguro.
